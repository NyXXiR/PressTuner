# 선택형 품질 검토 UI 어댑터

2026-10-13. 인증된 PressTuner 편집기의 기존 평가 영역에 연결했다. 기존 study domain/service/API와 Prisma는 변경하지 않는다. 공개 `/demo`의 평가 비교 소개 화면과는 별개다.

## 일반 작성자 화면 후속

사용자가 프로그래밍이나 평가 용어를 몰라도 쓰도록 기본 흐름을 다시 정리했다. 아래의 연구용 검토는 **평가기 관리 열기** 안으로 이동했고, 관리 영역을 열기 전에는 study 목록/질문/보고서를 요청하지 않는다. 별도의 문체 첨삭도 접힌 선택 기능으로 남긴다.

1. 편집기 상단 **원고에서 고칠 곳 찾기**에서 버튼 하나로 현재 원고의 G-Eval을 실행한다. 공식 Ragas/DeepEval 표준 실행·모델·점수·과거 이력은 **평가 방법·점수·기록**에서 그대로 확인한다.
2. 기준 미달 또는 Ragas의 근거 부족 신호가 있으면 문제 종류와 **고칠 부분의 수정안 받기**를 안내한다. 실행 실패, 평가 기준 없음, 변경된 원고를 합격으로 보여주지 않는다. 자동 확인 신호가 없다는 것이 사실 정확성 보증은 아니다.
3. 수정안 요청은 기존 `polish` → `re-polish`를 이용한다. 평가 설명은 오류 가능성이 있는 참고 데이터로 전달하며, 기존 서버의 채택 사실과 RISK note의 fact ID 검사를 유지한다. 위험 제안을 우선해 최대 3개 note를 선택한다. UI에 기존 첨삭/재작성 사용량과 최대 2회의 AI 호출을 명시하고, 실패/원고 변경/화면 이탈 뒤 다음 호출을 자동 진행하지 않는다.
4. 서버가 반환한 원본과 후보를 정확한 텍스트 변경으로 비교해 한 곳씩 **이 수정 반영 / 현재 문장 유지 / 나중에 확인**을 제공한다. 현재 문장·제안 문장을 함께 보여주고, note가 정확히 포함된 변경에는 연결된 현재 채택 자료를 표시한다. 평가 reason에서 대체 문장을 추측하지 않는다.
5. **반영**은 기존 `/save` API로 실제 원고를 저장한다. **유지/나중에**는 원고를 변경하지 않는다. 직전 반영 되돌리기, 미룬 변경 다시 보기, 저장 실패 안내·수동 재저장을 제공한다. 수정 뒤 기존 평가와 발행 검증은 다시 확인해야 한다.

변경 경계는 `quality-edit/adapter.ts`의 표시·정확한 변경 재구성, `revision.ts`의 기존 편집 명령 연결, `DraftRevisionChoices.tsx`, 기존 편집기/store다. LCS로 반복 문장의 위치와 원래 공백을 보존하며 긴 입력은 전체 변경으로 제한한다. 반영/되돌리기는 예상 제목·본문과 현재 편집 내용이 정확히 같아야 한다. 한 편집기 안의 자동 저장/명시 저장은 직렬화하며 늦은 응답이 새 입력을 저장 완료로 표시하지 않는다.

일반 작성자의 수정 선택은 연구의 `PRODUCT APPLY`나 PASS/FAIL 정답이 아니다. partial edit를 전체 rewrite 채택으로 기록하지 않고 기존 수동 편집 저장 경로를 따른다. 연구 보고서의 분모·정답·노출·회귀 판정은 바꾸지 않는다. 별도 모델/새 프롬프트 서버/교정 추론 엔진을 만드는 대안보다 기존 근거 기반 첨삭의 재사용을 선택했다. 그 대가로 수정안 생성에 최대 두 번의 추가 호출이 필요하다.

현재 한계:

- 실제 저장한 원고는 서버에 남지만, 변경 카드의 유지/나중에 상태와 되돌리기는 현재 화면 동안만 유지한다. 새로고침을 넘는 후보 복구는 후속이다.
- 원고 원본 확인은 현재 편집기 안의 충돌을 막는다. 기존 `/save` API에 서버 버전 CAS가 없으므로 다른 탭/기기의 동시 편집까지 보장하지 않는다.
- 연결 자료는 기존 첨삭이 참조한 사실이다. 새 문장 전체가 사실적으로 옳다는 증명이나 문장별 의미 검증은 아니다. 실제 모델의 수정 품질과 사용자 노력 감소는 아직 실증하지 않았다.

## 평가기 관리에서 사용하는 연구 흐름

1. 저장된 평가를 선택하거나 표준/업무 평가를 실행한다. 프레임워크·모델·점수는 상세 보기로 두고 근거 확인과 사실·과장 확인을 먼저 안내한다.
2. **이 평가에서 검토 시작**을 누르면 기존 실행 ID로 연구 생성 → 개발 표본 추가 → 고정 → PRODUCT 질문 배정을 연결한다. 이 준비는 모델을 호출하지 않는다. 관리자 권한이 필요하다.
3. 서버가 선정한 최대 3개 질문을 한 번에 하나씩 보여준다. 원고, 채택 근거, 자동 평가 설명을 함께 보여주고 **수정 필요 / 현재 내용 유지 / 나중에 판단** 중 하나를 누르면 즉시 저장한다. 다음 묶음을 자동 배정하지 않는다.
4. 자동 설명의 인용문 또는 수치·단위가 실제 원고에 있을 때 해당 문장을 먼저 표시한다. 이는 읽을 위치를 찾는 보조 수단이고 확정된 오류나 의미적 근거 매칭이 아니다. 일치하는 구간이 없으면 전체 원고를 보여준다. 전체 원고와 모든 근거는 항상 확인할 수 있다.
5. 선택은 서버의 revision과 함께 보존한다. 새로고침하면 이어서 검토하고, 저장한 선택은 펼쳐 수정할 수 있다. JSON 다운로드나 이유 작성은 필요 없다. 브라우저 세션이 끝나도 서버 기록은 팀 검토 목록에서 다시 선택할 수 있다.
6. 선택적으로 **평가기 검증에 참여하기**에서 개선/보정/독립 감사 질문을 받는다. 자동 설명과 설명에서 고른 발췌문을 숨기고 전체 원고를 보여준다. 자동 결과를 전에 봤는지 명시적으로 선택해야 하며 기본값을 `NONE`으로 넣지 않는다. 노출 이력의 최종 판단은 서버가 한다.
7. 관리자는 기존 실패에서 개선 비교를 준비하고, 별도 버튼으로 생성·평가를 실행한다. 한 번 누를 때 최대 4개 기존 `RUN_STEP` 명령을 순서대로 실행한다. 한 원문의 전체 비교는 생성 2회와 평가 2회이며, SDK 내부 모델 호출 수는 더 많을 수 있다. 실패·불확실 응답·화면 이탈 뒤에는 다음 단계를 자동 실행하지 않는다.
8. 준비된 A/B는 설정 이름을 숨기고 **A / B / 차이 없음 / 판단 어려움 / 건너뛰기**로 저장한다. 선호 기록과 개선안 채택은 별개다.
9. **결과와 개선 제안 보기**를 명시적으로 눌러야 관리자 보고서를 조회한다. 이 조회가 평가 노출로 기록되므로 블라인드 검토 중 미리 가져오지 않는다. 질문·A/B·관리자 보고서는 한 번에 하나만 표시한다. `HOLD`, `UNKNOWN`, 표본 부족을 사용자 언어로 전달하고 서버 조건이 충족되지 않으면 개선안 채택 기록 버튼을 비활성화한다.

품질 영역은 편집기 상단 전체 너비에 배치한다. 비교 카드는 실제 컨테이너 너비에 따라 두 열 또는 한 열이 된다. 평가 이력을 새로 불러오거나 다른 이력을 선택해도 진행 중인 연구 검토를 버리지 않는다. 다른 평가로 시작하려면 **현재 선택한 평가로 새 검토 시작**을 명시적으로 누른다.

## 경계와 선택 이유

- `components/press/quality-study/adapter.ts`: 기존 서비스 반환 타입을 type-only로 참조하는 브라우저용 표시 모델. 판단 기준·통계를 재계산하지 않는다.
- `client.ts`: 기존 엔드포인트 호출, 직렬 실행, revision 충돌 복구, 동일 idempotency key 재확인. 쿠키·원고·근거는 브라우저 저장소에 별도로 저장하지 않는다. 선택한 study ID와 미확인 요청만 sessionStorage에 보관한다.
- `ReviewCards.tsx`, `StudyReport.tsx`, `PressQualityStudyPanel.tsx`: 선택·복구·비교·결정 UI. `PressStandardEvaluationPanel`이 현재 평가와 연결한다.
- 새로운 BFF/API나 통계 엔진을 만드는 대안 대신 기존 API 위에 화면용 어댑터를 두었다. 서버의 권한, split, 사람 판정 provenance, 회귀 gate가 그대로 권위 있는 판단이다.
- PRODUCT의 `APPLY`는 기존 API에서 `RECORDED_INTENT_ONLY`다. 화면에는 **수정 필요**라고 표시한다. 실제 수정안을 원고에 적용했다고 말하지 않으며 자동 수정도 하지 않는다. 후보 채택 역시 연구 결정 기록으로만 남는다.
- 저장 응답이 유실되면 새 선택을 막고 **같은 요청으로 결과 확인**을 제공한다. 409 충돌에서는 최신 내용을 읽되 기존 선택을 자동 재전송하지 않는다.
- 시간 절약이나 평가기 신뢰도 향상을 구현만으로 주장하지 않는다. 실제 사람의 선택 수, 읽기 부담, 완료율과 독립 감사는 후속 측정이다.

## 검증

```powershell
npm run test:press-study-ui
npm run test:press-study-browser
npm run test:press-study
npm run typecheck:press-standard
npm run lint
```

- 어댑터/전송 계약 8개: 의도와 적용 구분, 블라인드 누출 차단, 노출 선택 필수, 저장 revision, HOLD/UNKNOWN, 미확인 요청 복구, 동시 호출/충돌, 실제 브라우저 fetch receiver, 원문 발췌의 근거를 확인했다.
- 브라우저 시나리오 1개: 실제 React 컴포넌트·제품 CSS·기존 study service/domain을 사용하고 저장소와 생성기/평가기는 합성 메모리 fixture로 격리했다. 모바일 선택 → 이력 변경에도 진행 유지 → 새로고침 → 서버 저장 뒤 503 응답 → 같은 key 복구 → 블라인드 질문 → 명시적인 모의 생성·평가 4단계 → A/B 선택 → HOLD/UNKNOWN 채택 차단을 확인했다. 큰 화면의 좁은 컨테이너에서도 한 열로 표시한다. 모델·DB·실제 사람 판정은 생성하지 않는다.
- 기존 백엔드 14개 테스트, 전용 타입 검사와 변경 파일 lint 통과. 전체 lint는 오류 0, 기존 경고 76개다.
- 모바일/데스크톱 합성 화면 스크린샷을 검사했다. 가로 넘침 없음, 질문 하나씩 표시, 전체 원고 접근, 원고/근거 가독성을 확인했다. 스크린샷은 외부 artifacts 경로에 있고 사람 판정 증거가 아니다.
- `npm run build`: Prisma 생성은 통과했으나 기존 Windows wrapper의 `spawnSync("npm", ...)` 단계에서 종료 코드 1. 같은 환경 파일을 읽어 Node로 Next CLI를 직접 실행한 production build로 별도 확인한다.

실제 편집기 시각 확인과 최종 빌드 결과는 [결과 기록](EVALUATION_SYSTEM_RESULTS.md)의 2026-10-13 절을 따른다. 테스트 DB의 일시적인 연결 실패와 UI 코드의 합성 검증 결과를 구분한다.

## 남은 범위

- 실제 사람 판정과 두 독립 평가자, 대표성 있는 데이터셋, Judge 보정·독립 감사·효과 실증.
- 실제 사람의 검토 부담 측정 및 장문 원고에서의 읽기 동선 조정.
- 문장별 의미적 근거 연결은 별도 설계 대상이다. 기존 첨삭의 후보를 변경 구간으로 나눠 실제 편집기에 적용하는 기능은 위 일반 작성자 후속으로 구현했다.
- 표본을 개발/보정/감사로 구성하고 보정 정책·회귀 명세를 고정하는 운영자용 데이터 관리 화면은 기존 CLI/API를 사용한다. 일반 검토 화면에서 임의 승격하지 않는다.
- 운영 DB 반영, 원격 CI와 배포는 포함하지 않는다.
