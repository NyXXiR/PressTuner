# 초안 품질 평가·개선 시스템 구현 결과

2026-10-12, 로컬 검증. 아래 본문은 [전체 계획](EVALUATION_SYSTEM_PLAN.md)의 최초 A~F 로컬 초안 평가 경로 구현 당시 기록이다. 이후 표준 2지표의 인증된 편집기 실행은 [표준 평가 버전](STANDARD_EVALUATION_VERSION.md)에서 구현·검증했다. 영속 평가 이력·편집기 G-Eval/사람 검토·평가기 신뢰도 입증 및 실제 Agent trace 평가(G)는 남아 있다. 현재 후속 순서는 전체 계획의 0~5를 따른다.

## 사용자가 할 수 있는 일

1. 같은 초안에 대한 Ragas의 근거 일치와 DeepEval G-Eval의 5개 업무 기준을 확인한다. 첫 화면에는 수정할 문제와 필요한 확인을 먼저 표시한다.
2. 자동 판단이 불확실하거나 충돌하는 항목을 선택으로 검토한다. 기본 질문 상한은 3개이며, 무작위 점검과 위험 우선 질문을 구분한다. 선택·판단 어려움·건너뛰기가 즉시 저장되고 재시작 후 복구된다.
3. 관측한 실패에서 개선 지침 후보를 만들고, 고정한 설정으로 기존/후보 초안을 각각 생성해 원문 단위로 비교한다. 기존 유지·후보 추가 검증·보류를 선택할 수 있다.
4. 사람이 확인한 실패를 회귀 요구사항으로 남긴다. 이후 실행에서 위반은 exit 1, 평가 누락/불확실은 exit 2가 되어 자동 검사에 연결된다.

기술 선택과 대안은 [평가 방법 설명](EVALUATION_METHODS.md), 실행 절차는 [실행 안내](EVALUATION_SYSTEM_RUNBOOK.md)에 있다. 실제 모델 호출은 별도 명령이며 화면의 선택만으로 호출하거나 운영 설정을 바꾸지 않는다.

## 실패에서 회귀 검사까지

[회귀 명세](../../../evals/press-workflow/regression/v1/manifest.json)는 C01의 사실 근거·과장 두 기준이다. 과거 여러 출력의 같은 과장 결함은 입력/기준 단위 하나로 합쳤다.

| 적용 대상 | 사실 근거 | 과장 | gate |
|---|---|---|---|
| 기존 저장 후보의 G-Eval 결과 | PASS | FAIL | REGRESSION / exit 1 |
| 개선 recipe로 새로 생성한 후보 | PASS | PASS | PASS / exit 0 |

이는 좁은 회귀 조건을 자동 검사한 결과다. 새 후보의 Ragas는 0.5이며 G-Eval 과장 점수는 0.8867이었다. G-Eval 설명 자체에도 가격 평가 표현에 대한 우려가 남았지만 실험용 0.8 threshold를 넘어서 PASS가 됐다. **gate 통과가 실제 결함 해소나 사람 승인이라는 뜻은 아니다.** 평가기 임계값과 판단 기준을 독립 자료에서 검증해야 한다.

신규 회귀 원본: `geval-regression-reevaluation-20261012.json`; gate: `geval-regression-after-result-20261012.json`. 같은 입력을 이미 개발에 사용했으므로 이 결과를 독립 holdout 개선으로 세지 않는다.

## 남은 목표와 순서

1. **평가기 검증:** 서로 다른 원문에 걸친 정상·결함 표본을 미리 선정하고 실제 사람이 선택한 판정으로 보정/독립 검증을 분리한다. 현재 rubric/0.8 threshold는 실험용이다. 기준별 미탐·오탐·불확실을 보고 판단 기준을 수정한다.
2. **효과와 사람 노력 측정:** 더 많은 독립 원문에서 동일 설정을 비교하고, 실제 선택 수·체류 관측·완료율·놓친 결함을 함께 측정한다. 질문 상한 10→3 구현은 확인했지만 실제 노동시간 감소는 미측정이다. 전체 초안을 읽는 부담도 남아 있다.
3. **제품 통합:** 현재 로컬 화면과 CLI 사이에서 실험을 실행한다. 독립 audit 입력은 CLI의 `compare --audit`로 지원하며 화면에는 아직 연결하지 않았다. 인증된 편집기에서 평가 요청·비용·팀 권한·기록·채택을 연결하는 통합은 별도다.
4. **Agent 확장(G):** 실제 retrieval/tool/task trace를 연결한 뒤 Contextual Precision/Recall, ToolCorrectness, TaskCompletion을 적용한다. 이번 draft-only 결과로 검색·도구 성능을 주장하지 않는다.

이번에 구현한 것은 평가에서 개선 실험과 회귀까지 이어지는 실행 가능한 로컬 시스템이다. 신뢰할 만한 평가기와 고객의 더 쉬운 의사결정이라는 최종 목표는 위 실증을 마쳐야 충족된다.

## Judge 점검 후속 0단계: 계획 개정과 CI 수정

2026-10-12 후속. [전체 계획](EVALUATION_SYSTEM_PLAN.md)에 현재 상태, 저장 계약, 0~5 단계별 완료 기준을 정리했다. 제품 수정 선택과 블라인드 감사 라벨 분리, 질문 상한, 보정/감사/holdout 구분, 평가자 간 일치, 실제 pairwise, 평가기 변경과 생성기 개선 비교의 분리까지 포함한다. 후속 1~5 기능 구현이나 신뢰도 실증이 완료됐다는 의미는 아니다.

기존 CI는 DeepEval 의존성만 설치하고 Ragas SDK 테스트도 실행했다. DeepEval 환경에서 기존 Ragas `test_requests.py`를 실행해 `ModuleNotFoundError: httpx`를 재현했다. 두 lock의 OpenAI 버전도 Ragas 1.109.1 / DeepEval 3.29.0으로 달라 한 환경에 합쳐 설치하지 않았다.

`.github/workflows/press-quality.yml`을 각 framework별 독립 runner matrix로 수정했다. Node job에는 표준 평가 테스트/타입 검사를 추가했고, 기사 API·편집기·관련 서비스·Next/TS 설정 변경에서도 실행되게 했다. 유료 모델 회귀는 기존 수동 opt-in을 유지하면서 무료 Node/SDK 검사가 성공한 뒤에만 시작한다.

총 테스트 66개 통과는 오프라인 코드/배선 검사 결과다. 이번 작업은 새 실제 모델 호출·사람 판정·GitHub 실행을 포함하지 않았다. 로컬 Node는 20.11.1이며 CI 지정 Node 22/Ubuntu의 새 의존성 설치부터 전체 실행까지는 아직 확인하지 않았다. 현재 G-Eval threshold나 Luna의 정확도가 이 CI 수정으로 검증되는 것은 아니다.

## Judge 점검 후속 1단계: 평가 이력과 업무 평가 연결

2026-10-12 위 후속 구현을 진행했다. `ArticleQualityEvaluation`에 입력·채택 근거·평가기 설정·실행 상태·지표별 결과를 저장하고, 편집기에 표준 평가와 업무 G-Eval 및 최근 10회 이력 선택을 연결했다. 원고/근거 변경은 이전 버전으로 표시하고, 동일 입력/평가기의 부분 재시도는 성공 항목의 원 실행을 표시하며 실패 항목만 호출한다. 기사 권한 검사, DB 동시 실행 예약, idempotency, 실행 만료 후 결과 보존을 포함한다.

현재 G-Eval은 실제 입력이 확보된 사실 근거·과장 기준만 실행한다. 필수 사실·문체 예시 혼입·요청 문체는 NOT_APPLICABLE이며 점수나 통과로 바꾸지 않는다. 기존 CLI의 5기준 평가 기능은 유지한다. 표준 모델은 Luna, G-Eval은 기존 4.1 mini다. G-Eval 0.8은 보정 전 실험 기준이다.

### 합성 데모 API 실측

별도 테스트 DB의 지정된 합성 기사에서 두 실행을 각 1회 수행했다. [원본 증거](../../../evals/press-workflow/evidence/2026-10-12-article-quality-history.json)는 실제 실행 profile hash와 지표 사용량을 보존한다.

| 지표 | 점수 / 상태 | 지표 실행 시간 | 입력 / 출력 토큰 |
|---|---|---:|---:|
| Ragas Faithfulness | 1.0 / COMPLETED | 9.88초 | 1,767 / 307 |
| DeepEval Faithfulness | 1.0 / COMPLETED | 11.39초 | 1,643 / 230 |
| G-Eval 사실 근거 | 1.0 / COMPLETED | 4.48초 | 675 / 101 |
| G-Eval 과장 | 1.0 / COMPLETED | 3.76초 | 664 / 72 |
| G-Eval 나머지 3기준 | 점수 없음 / NOT_APPLICABLE | 모델 호출 없음 | 0 / 0 |

각 실행은 같은 key 재전송에서 동일 실행 ID/결과를 반환했고 별도 GET에서 저장 결과가 복구됐다. 표준 실행 POST는 원격 테스트 DB 지연을 포함해 약 53초였다. SDK 시간과 사용자 대기 시간은 다르다. 모델 실행 뒤 tracing 설정/소스 hash 읽기를 보강했으므로 기존 실측 profile hash를 최신 구현의 실측으로 바꾸지 않는다. 최종 코드의 저장 이력 재조회는 `--read-only`로 별도 확인하며 추가 모델 호출을 하지 않는다.

이는 실행·영속 저장 검증이다. 작은 합성 초안의 1.0을 평가기 정확도, 사람 일치율, 제품 품질 개선으로 해석하지 않는다. 새 사람 판정이나 calibration은 수행하지 않았다.

## 새 연구 API의 실제 모델 왕복

2026-10-12 후속. 격리 테스트 DB의 새로운 합성 원문 한 개에 가격 모순·근거 없는 고객 수/시장 지위를 의도적으로 넣었다. 현재 화면의 데모 기사는 수정하지 않았다. 실제 공식 프레임워크 평가 → 저장된 실행 두 개를 DEVELOPMENT로 고정 → 같은 출력 STANDARD 재평가 → 개선 recipe 고정 → production generator의 baseline/candidate 별도 생성·GEVAL 평가 → 블라인드 A/B 질문 준비 → 보고서/export 재조회까지 완료했다.

원본: [실측 보고서](../../../evals/press-workflow/evidence/2026-10-12-study-live.json), [요청·저장 journal](../../../evals/press-workflow/evidence/2026-10-12-study-live.jsonl), [실제 생성 출력](../../../evals/press-workflow/evidence/2026-10-12-study-live-outputs.json), [회귀 CLI 결과](../../../evals/press-workflow/evidence/2026-10-12-study-live-regression.json). 합성 연구/기사는 재조회와 후속 검토를 위해 테스트 DB에 보존한다.

### 관측 결과

| 대상·지표 | 점수 | 해석 |
|---|---:|---|
| 결함을 넣은 원고 / Ragas Faithfulness | 0.25 | 기본 binary threshold 없음. 낮은 근거 지지 비율 |
| 같은 원고 / DeepEval Faithfulness | 0.6667 | 기본 0.5 기준 PASS. 이유에는 7,300원을 73,000원으로 쓴 오류를 명시 |
| 같은 원고 / G-Eval 사실 근거 | 0.2150 | 실험용 0.8 기준 FAIL |
| 같은 원고 / G-Eval 과장 | 0.2000 | 실험용 0.8 기준 FAIL |
| 새 baseline / G-Eval 사실 근거·과장 | 각각 1.0 | 사람 검증 없음. 실제 출력에서 후술한 미탐 후보 관측 |
| 새 candidate / G-Eval 사실 근거·과장 | 각각 1.0 | baseline 대비 점수 차이 0. 독립 개선 증거 없음 |

동일 출력 STANDARD 재평가에서도 0.25/0.6667이 나왔고 profile hash가 같았다. 이는 같은 설정으로 두 번 실행한 관측이며 새 Judge 모델과의 비교나 일반적인 재현성 입증이 아니다. 생성 개선에는 별도 고정한 GEVAL profile을 사용했다. G-Eval의 필수 사실/문체 예시 혼입/요청 문체는 여전히 NOT_APPLICABLE이다.

총 생성 2개, 평가 job 5개(실제 평가 metric 합계 10개), 유료 API 작업 7개였다. SDK 내부 HTTP 호출 수와 구분한다. 저장된 12개 사용량 기록의 합은 입력 13,908 tokens / 출력 3,387 tokens다. baseline/candidate 생성 사용량은 각각 1,204/927 및 1,398/603 tokens였다. 한 번씩의 소규모 관측으로 비용 절감·지연 개선을 주장하지 않는다.

### 평가기 검증을 위해 남긴 두 사례

1. **정책 검토:** DeepEval은 가격 모순을 이유에서 탐지했지만 지표 값은 기본 threshold를 넘었다. Judge가 오류를 전혀 보지 못한 사례와, 오류를 발견해도 업무 통과 기준이 허용하는 사례를 구분해야 한다. 이 결과에 맞춰 threshold를 즉시 바꾸지 않았다.
2. **미탐 후보:** baseline에는 근거에 없는 “앞으로도 사용자 편의성을 강화한 다양한 기능을 추가할 계획”이 있다. 현재 FACTUAL_SUPPORT rubric은 근거 없는 future plans를 위반으로 명시하지만, G-Eval은 1.0과 함께 추가 계획을 허용한다는 이유를 반환했다. 원문·출력·rubric·이유를 연결해 보존했다. [검토 후보](../../../evals/press-workflow/evidence/2026-10-12-study-live-findings.json)는 AI가 식별한 PENDING_HUMAN_REVIEW이며 사람 정답·실제 미탐률·회귀 명세로 자동 승격하지 않는다.

결론은 **HOLD**다. 실제 사람 판정 0개, 독립 감사/holdout/선호 투표 없음, 개발 원문 한 그룹뿐이며 회귀 명세도 없어 **UNKNOWN / exit 2**를 유지했다. 블라인드 A/B 위치는 저장했지만 사람 대신 선택하지 않았다. 1.0 점수나 생성 성공을 품질 보증으로 표시하지 않는다.

### 코드·재조회 검증

실측 과정에서 관리자 보고서에 고정 recipe/개선 지침과 각 출력의 평가 실행·원점수·이유가 빠져 있는 것을 보완했다. 두 누락을 먼저 테스트로 재현했고, 수정 후 study 계약 14개와 전용 standard 타입 검사가 통과했다. 일반 검토자의 블라인드 payload는 그대로다.

`study-live-check.mjs --read-only 2026-10-12-study-live`의 별도 로그인/조회에서 보고서 hash와 A/B 질문 hash가 복구됐으며 추가 모델 작업은 0개였다. 실제 인증된 `study-client.mjs regression`도 UNKNOWN과 종료 코드 2를 반환했다. 유료 요청 재전송 검사는 같은 Judge job/생성 step을 재사용했다.

전체 lint는 오류 0·기존 경고 76, 변경 파일 lint와 diff 검사는 통과했다. `npm run build`는 실행 중인 서버의 Prisma DLL 점유로 EPERM이 발생했으며, 생성된 client를 사용하는 최신 직접 Next production build는 152페이지와 종료 코드 0으로 통과했다. schema·scheduler·운영 DB 변경, 원격 CI, 화면 검증은 이번 후속에 포함하지 않았다.

남은 제품 단계는 이 저장 결과/가설/검토 후보를 선택형 화면에 연결하는 것이다. 이후 실제 사람이 검토한 사례를 기준 데이터로 삼아 보정·독립 감사를 수행해야 한다. 이번 발견은 그 절차가 필요한 구체적인 사례이며, Judge 신뢰도 실증을 대신하지 않는다.

## 2026-10-13: 백엔드를 유지한 선택형 검토 UI

위 화면 연결을 진행했다. 인증 편집기의 `PressStandardEvaluationPanel`에서 저장된 평가 → 검토 준비 → 최대 3개 질문 → 선택 자동 저장/복구 → 개선 후보 실행 → A/B → 보고/결정으로 이동한다. 프레임워크 점수는 상세 보기로 옮기고 원고·근거·필요한 행동을 먼저 보여준다. [UI 계약·재현 명령·한계](QUALITY_STUDY_UI.md)에 경계를 기록했다.

새 브라우저 어댑터만 추가했으며 study domain/service/API, DB 스키마, 생성/평가 모델, 통계·채택 정책은 변경하지 않았다. PRODUCT의 APPLY는 **수정 필요**라는 의견 저장이다. 실제 원고를 바꾸거나 정답으로 승격하지 않는다. 선택형 검증과 A/B의 노출 여부는 사용자가 직접 선택하며, 서버의 노출 이력·권한 판단을 유지한다. 보고서 GET은 명시적인 사용자 행동 때만 호출한다.

원고 발췌는 자동 설명에 등장한 인용문/수치가 실제 원고에 있을 때만 제공한다. 의미적 사실 검증이나 문장별 근거 검색을 새로 수행한 것은 아니다. 블라인드 검증에는 이 발췌도 사용하지 않는다. 미측정·불충분·HOLD/UNKNOWN은 성공으로 바꾸지 않는다.

### 검증과 실제 편집기 확인

- UI 어댑터·전송 테스트 8개, 기존 study domain/service 14개 통과. 실제 브라우저에서만 드러난 fetch receiver 문제를 실패 테스트로 재현한 뒤 수정했다.
- 실제 React·제품 CSS·기존 service를 사용하는 격리 브라우저 시나리오 통과. 메모리 저장소의 합성 판정만 사용했으며, 실제 사람의 정답·선호나 유료 모델 실행은 만들지 않았다. 저장 응답 유실 뒤 같은 요청 복구, 이력 변경 중 검토 유지, 모바일 및 좁은 컨테이너, 블라인드 노출 차단, 비교 실행 상한, 채택 차단을 포함한다.
- 전용 TypeScript 검사, 변경 파일 lint, diff 검사 통과. 전체 lint 오류 0, 기존 경고 76개.
- `npm run build`는 Prisma 생성까지 통과했으나 기존 Windows wrapper의 npm 하위 프로세스 실행에서 종료 1. 동일 환경 파일을 읽는 직접 Next production build는 최종 배치·복구 수정 뒤 152페이지 생성, 종료 코드 0으로 통과했다. 이 작업에서 자동 추가된 임시 build 디렉터리의 tsconfig include 2개만 제거했다.
- 실제 앱의 격리 테스트 DB 서버를 재개하고 기존 세션으로 편집기를 열었다. 초기 `/quality-evaluation`과 study 목록 읽기는 DB 연결 실패로 500을 반환했다. 코드/DB 설정을 바꾸지 않고 **저장 상태 새로고침**으로 목록을 복구하고, 2026-10-12에 저장한 실제 생성 A/B 두 원고를 UI에서 조회했다. 사람 판정·A/B 투표·채택·추가 모델 호출은 하지 않았다. 이 성공이 DB의 장기 연결 안정성을 입증하지 않는다.
- 실제 편집기의 기존 오른쪽 보조 칸이 비교 원고에 너무 좁아, 평가·검토 영역을 본문 전체 너비로 옮겼다. 각 카드도 viewport 대신 실제 배치 너비로 한 열/두 열을 결정한다. 좁은 컨테이너의 브라우저 검사로 재확인했다.

현재 첫 제품 연결은 구현됐다. 실제 사람이 선택한 독립 기준 데이터, 정확도·개선 효과, 실제 읽기 시간·노력 감소는 여전히 미측정이다. 문장 수정안의 원고 적용, 운영용 데이터 구성·보정/회귀 명세 관리 UI, 운영 DB/원격 CI·배포는 별도 범위다.

## 2026-10-13: 일반 작성자의 실제 수정 선택

사용자의 비개발자 사용성 피드백에 따라 기본 화면을 원고 확인 → 수정안 받기 → 변경 구간별 반영/유지/나중에로 정리했다. 품질 확인을 원고 위에 배치하고, 별도 문체 첨삭·평가 점수·A/B·Judge 검증은 접힌 영역에 둔다. 초기 화면은 study나 보고서를 조회하지 않는다.

새 UI는 기존 G-Eval과 `polish`/`re-polish`를 연결한다. 기존 근거 기반 첨삭 note를 최대 3개 선택하고, 반환된 후보를 원본과 정확히 비교한다. 변경 카드의 반영은 실제 `/save` 호출이며, 유지/나중에는 원고를 변경하지 않는다. 근거 ID가 연결된 첨삭에는 해당 현재 채택 자료를 표시한다. 설명 텍스트에서 숫자 교정안을 추측하거나 새로운 사람 정답을 만들지 않는다. 프레임워크·통계·study·API·DB·과금 백엔드는 그대로다.

검증 결과:

- `npm run test:press-edit-ui`: 8/8. 반복 문장·삽입/삭제·공백·소수의 정확한 재구성, 모델 요청 순서·중단, 오래된 변경 차단, 저장 실패, 저장 직렬화, 늦은 응답 보호, 기존 전체 적용 경로의 오래된 후보 차단을 포함한다.
- 위 명령의 격리 브라우저 검사는 실제 React 컴포넌트·store·제품 CSS와 합성 HTTP를 사용했다. 기본 G-Eval 실행 1회, 첨삭→재작성 각 1회, 문장 유지의 무변경, 반영·되돌리기·500 저장 실패→수동 재시도, 미룬 항목 재방문, 직접 입력 후 덮어쓰기 차단과 가로 넘침 없음을 확인했다. provider/DB 호출이나 실제 사람 판정이 아니다.
- 기존 study UI 8/8, domain/service 14/14, 기존 study 브라우저 1/1도 통과했다. 총 31개 검사(브라우저 시나리오 2개 포함).
- 전용 TypeScript 통과. 전체 lint 오류 0·기존 경고 76, 최종 변경 파일 lint 깨끗함. `git diff --check` 통과.

## 2026-10-13: 커밋 전 갈무리

[커밋 전 정리](RELEASE_READINESS.md)에 누적 변경·도메인 경계·배포 조건·후속 순서·제안 메시지를 모았다. README와 계획의 현재 상태를 과거 진행 이력에서 분리하고, 이미 연결한 UI를 미완료로 적은 표와 평가 이력의 새로고침 설명을 바로잡았다. 기존 런타임 동작은 바꾸지 않았다.

CI에 연구 UI·연구 브라우저·편집 UI 명령과 편집 store 변경 트리거를 추가하고 임시 standard-build 타입 경로를 제거했다. Node 무료 검사 10종 96개(격리 브라우저 3개 포함), Ragas 2개와 DeepEval 6개가 모두 통과했다. 전용 타입 검사 2종, 전체 lint(오류 0·기존 경고 76), diff/CI YAML/문서 링크 검사도 통과했다. 새 모델·DB 실행이나 사람 판정 없이 검증했으며, 빌드는 직전 결과를 보존하고 재실행하지 않았다.

Scheduler 작업 트리 schema는 본체와 byte 단위로 일치함을 확인했다. 해당 저장소의 기존 다른 변경은 보존했다. 커밋·푸시·운영 배포는 수행하지 않았다.
