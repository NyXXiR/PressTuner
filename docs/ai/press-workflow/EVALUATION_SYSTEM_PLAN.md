# 평가에서 의사결정까지: 전체 구현 계획

2026-10-12 합의 및 Judge 개념 점검 후 개정. 이전 DUAL_EVALUATION_PLAN의 실측·사람 판정은 보존한다. 아래 **후속 구현 순서**가 현재 작업 순서이며, A~G는 최초 설계 범위를 설명하는 기록이다.

## 성공 기준

1. 평가 개념/프레임워크를 적절하게 사용하고 원리, 선택 이유, 대안, 실제 효과와 한계를 코드·재현 명령·측정 보고서로 설명한다. G-Eval은 평가 방법이고 DeepEval은 이를 구현하는 프레임워크다. 도입과 정확도 개선은 별개다.
2. PressTuner 사용자가 평가 용어를 몰라도 근거를 확인하고 선택할 수 있는 adaptive UX를 구현한다. 업무 기준, 문제 종류, 판단 가능성에 따라 질문과 행동이 달라진다. 점수에 따라 색상만 바꾸는 것은 완료가 아니다.
3. 데이터셋 → 평가 → 실패 분류 → 개선 가설/설정 → 독립 실행 비교 → 회귀 검사까지 동일한 출처/버전으로 연결한다. 효과가 없으면 보류한다.

## 현재 상태와 완료의 의미

2026-10-13 제품 연결 후속: 기존 백엔드 0~5 위에 인증 편집기의 [UI 어댑터](QUALITY_STUDY_UI.md)를 구현했다. 선택형 검토·저장 복구·블라인드 질문·A/B·개선 실행과 관리자 보고/결정을 연결했다. 이어 일반 작성자 화면을 단일 G-Eval 확인 → 기존 첨삭으로 수정안 요청 → 바뀐 부분만 반영/유지/나중에 → 실제 원고 저장으로 정리했다. 연구 기능은 별도 관리 영역으로 접었다. 연구 PRODUCT는 여전히 수정 의견 기록이고, 새 일반 편집 선택과 사람 정답은 구분한다. 실제 사람의 독립 판정·개선 효과·사용자 노력 측정과 운영 배포는 완료되지 않았다.

표준 평가부터 연구·제품 화면까지 구현하고 로컬에서 검증했다. **현재 Judge의 독립 신뢰도·개선 효과·사용자 노력 감소는 아직 입증하지 않았다.** 기능 연결과 효과 입증을 구분하며, 커밋 범위와 배포 전 조건은 [커밋 전 정리](RELEASE_READINESS.md)를 따른다.

| 개념/기능 | 확인한 구현 | 남은 일 |
|---|---|---|
| 표준 LLM-as-a-Judge / Pointwise | 편집기에서 Ragas 0.4.3 Faithfulness와 DeepEval 4.2.8 FaithfulnessMetric 실행. Luna 기본 모델, DB 영속 이력·스냅샷·부분 재시도 구현 및 API 실측. 실제 편집기 조회와 격리 브라우저 동작 검증 | 운영 환경 실행 검증. 두 프레임워크가 같은 모델을 쓰므로 서로 독립적인 정확도 증거로 보지 않음 |
| 업무별 G-Eval | 공식 GEval을 편집기에 연결. 사실 근거·과장 2기준 실제 실행·저장·조회. 모델/rubric/구현 hash 추적 | 필수 사실·요청 문체·생성에 사용한 문체 예시 입력 연결. 현재 해당 3기준은 NOT_APPLICABLE. 4.1 mini와 실험용 0.8 유지 |
| Golden dataset | 기존 합성 자료/사람 판정 보존. 연구 DB에 고정 source·출력·metric별 reference, 연구 간 split 누출 방지 및 export 구현 | 새 실제 사람 기준 데이터 수집과 대표성 확인 |
| Judge calibration | 같은 출력 재평가, 보정 threshold 고정, 별도 감사의 혼동행렬·미탐/오탐·coverage·그룹 구간 backend 구현 | 현재 모델·rubric 조합의 실제 독립 감사 |
| Inter-rater agreement | 독립 reviewer의 원 판정/revision, raw agreement/kappa/분모, 불일치 시 reference 보류 구현 | 실제 두 사람 판정 수집, 별도 합의 UX |
| Pairwise | 실제 생성 A/B의 위치 무작위화·블라인드 payload·선택 revision과 pointwise의 별도 보고 구현. 관리 UI와 저장 복구 연결 | 실제 사용자 선호 측정 |
| Regression | 기존 CLI 보존. 연구의 사람 확인 개발 결함 승격, 입력/profile별 PASS/REGRESSION/UNKNOWN, backend CLI와 CI 계약 연결. 새 연구의 실제 모델 왕복 뒤 명세 없는 UNKNOWN/exit 2 확인 | 실제 사람 확인 결함의 연구 회귀 명세 및 원격 CI |
| Adaptive UX | 인증 편집기에 일반 수정 선택과 연구 검토 UI 연결. 변경 구간별 실제 저장·되돌리기·수동 재시도, 최대 3개 연구 질문과 연구 선택 저장/복구 구현 | 일반 수정 후보의 새로고침 복구, 서버 저장 충돌 방지, 실제 수정 품질·사용자 노력 측정 |

이전 G-Eval은 사람 판정과 8/10 일치했지만 사람 결함 3개 중 1개만 탐지했다. 이 결과는 **이전 모델의 작은 보정 표본**이다. Luna 표준 평가의 정확도나 독립 감사 결과로 옮겨 쓰지 않는다. 기존 상세 증거는 [구현 결과](EVALUATION_SYSTEM_RESULTS.md), 표준 화면의 실측과 한계는 [표준 평가 버전](STANDARD_EVALUATION_VERSION.md)을 따른다.

## 후속 구현 순서

### 2026-10-12 백엔드 우선 변경

이 절은 당시 구현 순서와 완료 조건의 기록이다. 후속 UI 연결은 위 현재 상태에 반영했으며, 독립 사람 검증·원격 CI·운영 배포는 계속 남아 있다.

사용자가 화면 검증을 나중으로 미루고 나머지 단계의 백엔드를 먼저 연결하도록 범위를 조정했다. 아래 2~5의 데이터·API·실행 계약을 한 흐름으로 구현한다. UI 통합, 실제 사람 라벨 수집, 독립 감사의 통계적 충족, 원격 CI/운영 배포는 별도 완료 축이다.

| 백엔드 단위 | 계약과 완료 기준 |
|---|---|
| 연구 데이터 | 팀 범위 `PressQualityStudy`: 저장된 기사 평가 ID로 서버 스냅샷을 가져와 원문 그룹/개발·보정·감사·holdout을 고정. 같은 기사·공유 출처는 split을 넘지 못함 |
| 검토 | 회당 최대 3개 서버 선정 질문, 실제 로그인 reviewer, 선택/노출 여부/revision/시각 보존. 제품 적용 선택과 기준 라벨 분리. 감사 payload는 점수/모델/이유를 숨김 |
| 신뢰도 | 고정 evaluator별 혼동행렬·미탐·오탐·coverage, 그룹 단위 구간, 독립 reviewer 간 raw agreement/kappa. 보정 partition만 threshold 후보에 사용하고 감사 개시 전 고정. 부족한 표본은 INSUFFICIENT |
| 개선 | 개발 실패에서 가설과 구체 지침 diff를 고정. 실제 production generator로 새 baseline/candidate를 생성하는 명시 실행 단계, 동일 judge recipe, blind A/B/동률/불확실 선택. 실행과 검토의 실패/중단을 보존 |
| 회귀 | 확인된 개발 결함만 버전 명세로 승격. 고정 입력·평가기와 결과를 비교하여 PASS/REGRESSION/UNKNOWN. 계약 CI와 인증된 backend replay 명령 제공 |

범위 예외: `app/api/press/quality-studies/`, Prisma의 연구 aggregate 및 scheduler mirror, 관련 CI/package/타입 설정. 원문 점수·사람 ID를 요청에서 신뢰하지 않는다. aggregate는 크기와 표본 수를 제한하며 모델 호출은 트랜잭션 밖에서 수행한다. 변경 전후 효과를 주장하려면 추후 실제 사람 검토와 독립 표본이 필요하다.

아래는 실행 순서와 완료 기준을 고정한 계획이다. 0~1 구현에 이어 2~5의 backend v1을 연결했다. [백엔드 계약과 한계](QUALITY_STUDY_BACKEND.md)를 따른다. 새 domain/service 14개, 실제 DB 계약 8개, 인증 HTTP 저장·검토·보고/export 검사 14개가 통과했다. 연결 단절로 미완료였던 HTTP 검증은 재개 후 완료했고 임시 데이터도 정리했다. 이어 새 study API에서 합성 한 원문의 생성 2개·평가 job 5개 및 별도 재조회를 실측했다. 점수만으로 채택하지 않고 HOLD/UNKNOWN을 유지했으며, DeepEval 기본 threshold와 G-Eval 미탐 검토 후보를 기록했다. 최신 코드의 직접 Next production build도 통과했다. 화면 연결·검증, 사람 신뢰도/개선 실증, 일반/운영 DB 반영, 원격 CI는 별도 완료 항목이다.

|---|---|---|---|
| 0. 재현 가능한 기반 | Ragas/DeepEval SDK CI 환경 분리, 표준 평가 테스트·타입 검사·변경 경로 연결 | 변경으로 평가 실행이 깨지는 것을 조기에 확인 | 두 SDK를 각 lock 환경에서 검사하고 표준 계약 검사가 통과. GitHub 실행은 로컬 결과와 별도 기록 |

### 1단계의 구체적인 구현 단위

첫 구현은 **평가 실행 → 저장된 결과 조회 → 새로고침 복구**라는 한 경로다. 일반용 대시보드나 범용 평가 빌더를 먼저 만들지 않는다.

1. `domain/press-workflow/evaluation/`에 실행·판정·검토 identity와 저장소 port를 정의한다. `standard.ts`, 기존 evaluator 계약과 해시 함수를 재사용한다.
2. `lib/services/press-workflow/evaluation/`에서 서버가 읽은 기사/채택 fact 스냅샷으로 평가 실행을 구성한다. 기존 standard runtime과 G-Eval 어댑터를 호출하며, 프레임워크 자체 점수/이유를 보존한다.
3. 팀/기사 소유권을 확인한 서버 저장소와 조회 API를 붙인다. Prisma 변경 전 스케줄러의 schema 동기화 범위를 확인하고 함께 검증한다. 임시 CLI JSON을 운영 저장소로 쓰지 않는다.
4. `PressStandardEvaluationPanel`에 저장 이력과 상세를 연결한다. 표준 2지표는 기존 기본 실행을 유지하고, 추가 비용이 드는 업무 G-Eval은 별도 실행으로 먼저 제공한다. G-Eval의 모델 변경도 별도 평가기 버전으로 취급한다.
5. 동기 실행을 우선 유지하되 결과를 DB에 기록한다. 재시도는 실패한 지표만 새 시도로 남기고, 요청 중단/타임아웃은 미완료 또는 실패로 드러낸다. 장시간 백그라운드 작업은 실제 지연/배포 요건이 확인되면 별도 작업으로 확장한다.

저장 계약은 다음을 포함한다. 세부 DB 이름은 구현 시 기존 모델과 맞춘다.

| 기록 | 반드시 남길 내용 |
|---|---|
| 평가 실행 | 팀/기사, 입력·초안·채택 fact의 해시와 재현 가능한 스냅샷, 생성 버전(알 수 없으면 UNKNOWN), evaluator 설정/구현/SDK 버전 해시, 시작/종료/시도 상태 |
| 지표 결과 | 지표·기준 ID, 원래 점수 척도와 임계값/보정 상태, 설명/근거 참조, 사용량·소요 시간, 오류·불확실. 실패를 0점으로 대체하지 않음 |
| 사람 검토 | 실행/출력/기준 identity, 실제 reviewer ID, 선택·시각·revision, 자동 판정 노출 여부, 질문 선정 이유/확률, 테스트 여부. 원래 독립 판정과 후속 합의를 별도 보존 |
| 기준 데이터 | 원문 그룹, 기대 결과/criterion label, AI_AUTHORED 또는 HUMAN_VERIFIED의 적용 범위, 검토 근거, split/version 및 보정 사용 이력 |
| 개선 실험 | baseline/candidate 생성 recipe, 동일 평가 recipe, 신규 생성 출력, pairwise 배치 순서·선택, 회귀 명세·결과 및 최종 사람 결정 |

같은 기사가 편집되면 이전 결과는 **이전 버전 평가**로 표시한다. 재요청용 idempotency key와 실행 시도 ID를 구분해 이중 클릭에 의한 중복 호출은 막되, 의도한 재평가는 허용한다. 수정 검토 기록은 revision 충돌을 알리고 기존 결과를 덮어쓰지 않는다. 원문/초안은 팀 권한 안에서만 제공하고 공개 증거에는 원문 대신 집계·해시를 사용한다.

### 사람이 하는 일과 자동화하는 일

| 상황 | 시스템이 준비할 것 | 사람이 할 선택 |
|---|---|---|
| 일상적인 초안 검토 | 자동 판정·문제 문장·연결된 fact·수정 제안 | 제안 적용/유지/보류. 이 선택 자체는 객관적인 정답 라벨이 아님 |
| 불확실/불일치 항목 확인 | 기준 하나, 관련 초안/근거, 필요하면 전체 원문 펼치기 | 충족/위반/판단 어려움. 이유 입력은 선택 |
| Judge 품질 감사 | 자동 점수·모델명을 숨긴 별도 선정 표본, 평가 기준 | 같은 세 가지 선택 또는 건너뛰기. 이 검토의 검증된 범위만 기준 데이터 후보 |
| 개선안 비교 | 이름을 숨긴 A/B 초안, 동일 원문과 요청 조건 | A/B/동률/판단 어려움. 이후 품질·회귀 보고서를 보고 채택 여부 선택 |

제품 검토는 문제 해결을 돕기 위해 자동 설명을 보여 준다. **정확도 감사용 검토는 자동 설명을 숨긴다.** 둘을 혼합해 모델과 사람의 높은 일치율을 만들지 않는다. 업무 사실의 선택과 문체 선호 선택도 구분한다.

처음에는 사용자 작업 1회당 검토를 최대 3문항으로 제한한다. 위험 우선 질문과 별도 무작위 감사 질문은 선정 경로를 기록하고 통계를 분리한다. 위험 표본에서의 미탐/오탐 비율을 전체 사용자 모집단 비율처럼 보고하지 않는다. 추가 감사는 운영 담당자용 검토 묶음으로 제공하며 모든 고객에게 매번 라벨 작성을 요구하지 않는다. 표본이 부족하면 검사 기능은 계속 쓰되 신뢰도만 **검증 부족**으로 표시한다.

### 데이터·보정·일치도 설계

- 기존 사람 판정 10개는 같은 출력 hash에만 연결해 현재 평가기를 비교한다. 표준 Faithfulness와 업무 기준은 정의가 같지 않으므로 5개 업무 라벨 전부를 Faithfulness 정답으로 취급하지 않는다. 대응이 확인된 사실 근거 기준만 비교하며, 주장 단위 정답이 없으면 세밀한 점수 정확도는 미측정으로 둔다.
- 데이터 구축은 다양한 원문의 정상/오류 사례, 날짜·수치 변경, 필수 사실 누락, 과장, 문체와 근거 혼입을 포함한다. 자동 생성 사례는 사람이 확인하기 전까지 AI_AUTHORED다. 기존 30개 합성 그룹은 준비 자료이며 검토 없이 golden으로 이름만 바꾸지 않는다.
- 개발/보정, Judge 독립 감사, 생성 개선 holdout을 **원문 그룹 단위**로 분리한다. 같은 원문의 여러 초안이 양쪽에 섞이지 않게 한다. 감사 실패를 보고 조정했다면 그 표본은 보정 이력에 남기고 새로운 감사 표본을 사용한다.
- 정상/결함 비율과 누락을 명시한 혼동행렬, 결함 recall, 오탐률, precision, 단순 일치율, coverage를 기준별로 보고한다. 표본 단위가 반복 초안이면 원문 그룹을 고려한 구간을 사용하고 충분하지 않으면 구간 미산출 이유를 표시한다. 점수 평균이나 일치율 하나로 신뢰 판정을 내리지 않는다.
- 두 사람이 독립적으로 평가한 일부 동일 표본에는 raw agreement와 Cohen's kappa를 함께 보고하고 정상/결함 분포, 표본 수, 계산 불가를 표시한다. 두 번째 검토자가 없으면 미측정이다. 한 사람의 반복 검토나 두 LLM을 여러 사람의 일치도로 바꾸지 않는다. 불일치는 선택형 재확인/합의로 처리하며 합의 전 판정도 보존한다.
- 임계값은 보정 데이터에서 조정한 후 고정한다. DeepEval Faithfulness의 0.5 기본값과 G-Eval의 0.8 실험값은 업무상 허용 품질을 입증하지 않는다. 현재 코드의 10그룹 등 최소 조건은 실험용 screening 정책이며 통계적 보증 기준이 아니다.
- 정확도/허용 미탐 목표와 표본 계획은 실패 비용 및 관측한 불확실성을 기준으로 문서화한다. 초기 소표본은 실행·분류 확인에 사용한다. 충분한 감사 자료 없이 임의의 표본 수를 채웠다는 이유로 자동 채택을 활성화하지 않는다.

### 개선·Pairwise·회귀 설계

실패 분류마다 개선 제안에 연결된 사례와 적용될 설정 diff를 제시한다. 모델이 제안한 원인은 **가설**로 표시한다. 근거 부족에는 자료 보완, 사실 혼입에는 입력/프롬프트 분리, 문체 문제에는 문체 지침 후보 등으로 행동을 구분한다. 확인된 근거 없는 사실을 자동으로 보충하지 않는다.

Pairwise는 문체·가독성 등 상대 선호가 필요한 개선 실험에 도입한다. 사실 근거의 pointwise 검사는 계속 별도로 실행한다. A/B 위치를 무작위 배정하고 설정명을 숨기며 동률/판단 어려움을 허용한다. LLM pairwise judge를 추가할 경우 위치를 바꾼 일부 재평가로 순서 편향을 점검하고 사람 선택과 분리해 저장한다. 좋은 문체가 사실 결함을 상쇄하도록 점수를 합산하지 않는다.

생성기 개선 비교에서는 judge recipe를 고정한다. judge 모델이나 rubric을 바꾸는 실험은 **같은 고정 출력**을 다시 평가하고 사람 기준에 대조한다. 두 변경을 동시에 섞어 점수 상승을 생성 품질 개선으로 해석하지 않는다. holdout에서 본 실패를 개발 회귀로 승격하면 그 표본은 더 이상 미사용 holdout이 아니며 split 이력을 갱신한다.

기존 regression CLI의 PASS/REGRESSION/UNKNOWN과 exit 0/1/2를 재사용한다. 무료 CI는 코드 계약과 알려진 합성 결함을 검사한다. 실제 모델 회귀는 고정 데이터·모델·budget으로 명시 실행하고, 자동 수동 판정이나 최종화 권한 변경을 포함하지 않는다. 표준 Faithfulness와 G-Eval은 각자의 명세/임계값을 검사하며 서로의 점수를 대체하지 않는다.

### 단계별 검증과 최종 데모

새 기능은 domain/service 실패 사례부터 작성한 뒤 API와 화면을 연결한다. 권한 없는 조회, 수정된 초안에 오래된 결과 표시, 이중 실행, 일부 평가 실패, 중단 후 미완료, 선택 저장 실패/충돌, 감사 데이터 누출, 다른 judge identity로 회귀 비교 등을 검증한다. 문서·CI 배선 수정에는 구현 내용을 반복하는 테스트를 추가하지 않고 실제 관련 명령을 실행한다.

최종 데모는 하나의 원문에서 **초안 생성 → 표준·업무 평가 → 근거가 있는 문제 카드 → 필요한 사람 선택 → 저장된 기준/실패 → 개선 후보 생성·비교 → 회귀 결과**를 연결한다. 원리/사용 이유/대안/효과는 [평가 방법](EVALUATION_METHODS.md)에, 실제 표본·사용량·오류와 미측정 효과는 [구현 결과](EVALUATION_SYSTEM_RESULTS.md)에 누적한다. 프레임워크 실행 성공, 시스템 연결 완료, 평가기 신뢰도 검증, 실제 사용자 노력 감소를 각각 별도 결과로 보고한다.

검색 Contextual Precision/Recall과 Agent Tool Correctness/Task Completion은 실제 검색/도구 trace를 붙이는 G단계에 남긴다. 현재의 채택 fact 기반 초안 평가를 검색기 성능 검증으로 표현하지 않는다.

## 최초 계획 당시 출발점 (이력)

- production articleGenerator를 재사용하는 headless 실행기와 Ragas 0.4.3 Faithfulness가 있다.
- 최초 계획 당시 업무 평가는 자체 단일 JSON judge였다. 이를 G-Eval이라고 부르지 않는다.
- 기준은 사실 근거, 필수 사실, 표현 예시의 사실 혼입, 과장, 요청 문체의 5개다.
- 원문 그룹 통계, 블라인드 선택/자동 저장, Console 숫자 요약이 있다. 현재는 초안 단위로 모든 기준을 검토한다.
- 기존 1원문/2초안/10사람 라벨은 비교 가능 5개 중 일치 3, 사람 결함 3개 중 탐지 0이다. 보정 자료이며 새로운 독립 검증 자료가 아니다.
- 별도 Press Agent에 검색·검증·적용 도구, 검색 결과/단계 기록, 실험 구조가 있다. 실제 agent trace가 없는 초안 평가를 검색/도구 평가로 포장하지 않는다.

## 책임과 데이터 흐름

데이터셋/생성/평가 artifact → 순수 분석·의사결정 도메인 → 프로젝트 로컬 선택 UI와 실험 CLI → 회귀 명세와 결과 → 기존 Console 읽기 전용 요약.

Ragas는 FACT 근거 일치의 표준 관점, DeepEval G-Eval은 고정한 업무 기준의 관점을 제공한다. 각 기준의 결과를 보존하고 합성 종합점수는 만들지 않는다. 기존 judge와 좁은 코드 검사를 비교 대안으로 유지한다. 라이브러리마다 잘하는 영역이 겹친다는 점을 설명한다.

## 최초 설계 범위와 종료 조건 (A~G)

| 단계 | 구현/산출물 | 종료 조건 |
|---|---|---|
| A. 계획/계약 | 이 문서, 버전·출처·실험/판정 계약 | 아래 단계와 검증 시나리오가 구현 전에 고정됨 |
| B. 평가 어댑터 | pinned DeepEval G-Eval, 고정 rubric/steps, Ragas 재사용, 기존 judge 선택 | 실제 라이브러리로 실행 가능; 오류와 판단 불확실 구별; 설정·score·사용량 추적 |
| C. 데이터/분석 | 기존 versioned dataset 재사용, 실패 분류, 사람 대비 criterion별 혼동행렬/coverage | AI 기대값과 사람 라벨 분리; 동일 출력에서 대안 비교; 0분모/누락을 성공 처리하지 않음 |
| D. adaptive UX | 기준 단위 검토, 근거와 초안의 필요한 범위, 상세 펼치기, 상태별 행동, 자동 저장 | 전체 기준 반복 검토 해소; 상한·무작위 감사 유지; 선택/건너뛰기/복구/충돌 확인 |
| E. 개선/회귀 | 원인→개선 설정, 고정 recipe, 별도 baseline/candidate 실행, 회귀 승격 및 gate CLI | source/output/evaluator identity 일치; regression/unknown 별도 종료코드; 채택은 사람 결정 |
| F. 자동화/실증 | 무료 계약 검사 CI, 명시 실행 live 평가, 기술 선택/실험/UX 문서 | 새 실패를 회귀로 재현; 실제 결과와 합성 QA 구분; 측정하지 않은 효과는 미측정 표시 |
| G. Agent 확장 | 실제 trace→검색/도구/완료 지표 어댑터 | 추적 자료에 필요한 필드가 있을 때만 실행; 승인/실제 저장 상태 코드 검증; v1 초안 실증과 별도 결과 |

최초 완결 시나리오는 기존 초안 생성·평가 경로의 A~F다. G도 전체 계획에 포함하지만 trace 연결과 runtime 검증은 별도의 종료 조건을 가진다. draft-only 경로에서 검색·도구 지표는 해당 없음으로 명시한다. 사용자 전체 목표의 완료와 부분 단계 완료를 혼동하지 않는다.

## 신뢰도·통계·데이터 규칙

- 평가 recipe 고정과 평가기 신뢰도 판정은 분리한다. 모든 검토/무불일치를 recipe 고정의 전제 조건으로 삼지 않는다.
- 사람 calibration 데이터는 재사용하고 judge 보정에 쓰지 않은 audit 사례를 따로 확보한다. generation holdout도 개발에 쓰지 않는다.
- 사람이 보지 않은 합성 정답은 AI_AUTHORED다. 검토되지 않은 정답/자동 선택을 HUMAN으로 올리지 않는다.
- 기존/후보는 동일 입력·평가 설정으로 별도 생성한다. 과거 출력 편집 replay를 실제 개선 실험으로 취급하지 않는다.
- failure taxonomy: 생성 실패, 평가 실행 실패, 판단 불확실, 사실 오류, 누락, 사실 혼입, 과장, 문체.
- 사람 대비 TP/FP/FN/TN, 비교 가능/전체 수, 불확실/누락을 함께 표시한다. 위험 우선 표본과 무작위 감사를 분리한다.
- 효과는 원문 그룹별 paired 비교와 표본/구간을 제시한다. 합성 benchmark와 production 모집단을 구별한다.
- 가격표 없이 비용 절감액을 추정하지 않는다. 사용 token·호출수·소요 시간은 관측한 값만 저장한다.

## UX 규칙

- 첫 화면은 필요한 행동과 근거, 기술 지표/프레임워크는 상세 보기다. 일반 초안 사용과 생성 설정 채택은 다른 결정이다.
- 중요한 결함→수정 검토, 근거 부족→자료 확인, 판정 불확실→사람 선택, 표본 부족→보류, 검사상 문제 없음→검사 범위를 표시한다.
- 감사 목적의 사람 검증은 자동 판정/설정 이름을 숨긴다. 제품 수정 검토에는 설명을 제공하되 감사 표본과 구분한다. criterion별로 하나씩 보여 주되 누락/전체 사실 판단에 필요한 전체 원문은 축약으로 감추지 않는다.
- 선택 즉시 저장, 건너뛰기는 미판정, 판단 어려움은 별도 상태. 이유/이름/JSON 저장을 요구하지 않는다.
- 검토 상한은 질문 수로도 제한한다. 일부 미검토는 전체 시스템 중단 조건이 아니다.
- 선택 횟수와 화면 체류 관측값은 실제 UI 이벤트만 기록한다. 자동 QA 시간을 사람의 시간 절감 근거로 쓰지 않는다.
- 사용자 선택은 해당 사례/버전에 묶는다. 조용한 자동 학습이나 운영 설정 변경을 하지 않는다.

## 검증 계획

실패 테스트 먼저: G-Eval identity/partial failures, human confusion matrix/selection bias, criterion budget/unknown, regression provenance/holdout mismatch, CLI exit codes, 저장 복구/충돌.
Python 공식 metric 객체의 offline contract 검사와 TS 주입 port 테스트를 병행한다. API-key 없는 CI는 계약/합성 테스트이며 모델 품질 PASS가 아니다.
로컬 브라우저는 모바일/데스크톱에서 질문 선택, 상세 근거, 저장/새로고침, 보류와 분석 연결을 확인한다.
마지막에 전용 test/typecheck, 변경 lint, 전체 lint/build, git diff --check를 실행한다. 환경 실패는 결과에 그대로 기록한다.

## 변경 경계

기존 workflow/evaluation 폴더 및 문서/명령을 중심으로 구현한다. 표준 편집기/API의 이미 허용된 변경 경계는 STANDARD_EVALUATION_VERSION.md를 따른다. 후속 1~2단계에서는 같은 기사 평가 API·서비스·컴포넌트에 이력과 검토를 연결한다. 영속화에 필요한 Prisma와 대응 scheduler schema는 해당 단계에서 도메인 규칙·권한·동기화 검증을 포함해 변경한다. 결제 정책, 생성/최종화 권한, 범용 Console 계약을 함께 개편하지 않는다. 기존 Console summary 계약은 유지한다.

## 진행 증거

최초 계획 수립 시점에는 새 기능 구현/실측이 없었다. 이후 로컬 시스템과 표준 편집기를 구현·실측했으며 각 시점의 결과는 EVALUATION_SYSTEM_RESULTS.md와 STANDARD_EVALUATION_VERSION.md에 보존한다. 이번 후속 0단계의 CI 수정 결과는 EVALUATION_SYSTEM_RESULTS.md에 별도로 추가한다. 1~5단계는 이 계획 개정만으로 구현 완료가 되지 않는다.
